# lib/middleware/auth.ts

## Что делает файл

Это middleware аутентификации для serverless API-функций.
Файл извлекает Bearer-токен из заголовка `Authorization`, проверяет его через Firebase Admin и записывает `req.userId` для следующих слоев.
Если токен отсутствует или невалиден, middleware возвращает `401` и останавливает дальнейшую обработку.

## Импорты и зависимости

1. `@vercel/node` (`VercelResponse`) - типизация HTTP-ответа в Vercel API.
2. `../../api/_firebaseAdmin` - инициализированный Firebase Admin SDK для проверки ID-токена.
3. `../types/request.types` (`AuthenticatedRequest`) - тип запроса с полем `userId`.

## Экспорты и контракты

1. Экспортируется функция `verifyAuth(req, res): Promise<void>`.
2. Контракт входа:
3. `req.headers.authorization` должен содержать строку формата `Bearer <token>`.
4. Контракт выхода:
5. При успехе функция завершает выполнение и устанавливает `req.userId`.
6. При ошибке отправляет `401` и бросает исключение `Unauthorized`.
7. Инварианты:
8. После успешного `verifyAuth` downstream-слои могут считать `req.userId` заполненным.
9. Middleware не возвращает данные пользователя в ответ, только id для авторизации операций.

## Нетривиальная логика

1. Проверяется не только наличие заголовка, но и обязательный префикс `Bearer `.
2. Любая ошибка в `verifyIdToken` (просроченный/битый токен) обрабатывается одинаково: `401` без утечки внутренних деталей.
3. Middleware использует исключение после отправки ответа, чтобы верхний слой (`api/items/index.ts`) прекратил выполнение контроллера.

## Где используется

1. Прямое использование в `api/items/index.ts` перед маршрутизацией методов.
2. Зависит от `api/_firebaseAdmin.ts` для доступа к Firebase Admin SDK.
3. Влияет на `lib/controllers/item.controller.ts`, потому что контроллеры ожидают валидный `req.userId`.
